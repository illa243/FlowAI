# Deep research у FlowAI

Дослідницький Flow розкладає велику тему на окремі завдання, збирає докази,
перевіряє кожен результат і формує підсумок. Цей довідник описує налаштування
звичайних Executor і Task Reviewer у FlowAI 0.4.0 станом на 3 вересня 2026 року.

## Що підтримує програма

Окремої ноди, кнопки або API-конектора Deep Research у FlowAI немає. Доступний
спосіб — підключити інструкції Deep research до агента, який працює через
Codex SDK, і перевірити наявність потрібних пошукових інструментів у його
середовищі. Назва Flow або вибір моделі самі по собі не вмикають пошук.

Поле **Скіли** показує локальний каталог `%USERPROFILE%/.codex/skills`.
Skill, встановлений у кеші plugin, може не з'явитися там. У такому разі
підключіть наявний `SKILL.md` через **MD-інструкції**. FlowAI прочитає текст
і додасть його до постійних інструкцій ноди.

## Підготовка

1. Створіть окрему теку Flow. Збережіть у `brief/` опис продукту, аудиторії,
   стадії розробки, бюджету й невідомих даних. Позначайте припущення явно.
2. Підготуйте інструкції Deep research у `instructions/deep-research/` або
   вкажіть шлях до встановленого skill. Якщо він посилається на інші файли,
   додайте їх або забезпечте доступ за правильними шляхами.
3. У поточному Codex перевірте доступ до вебпошуку й відкриття джерел.
   MD-файл не встановлює інструментів, браузера, plugin чи підключень до сервісів.
4. Задайте формат результату: звіт, список джерел, журнал пошуку, таблиці
   рекомендацій і перелік прогалин. Для кожної категорії використовуйте
   власну підтеку `artifacts/<task-id>/`.

Приклад фрагмента конфігурації Executor після створення зазначених файлів:

```json
{
  "prompt_source": "input",
  "sandbox": "workspace-write",
  "memory": "task_thread",
  "instruction_files": [
    "instructions/deep-research/SKILL.md",
    "instructions/research-protocol.md"
  ],
  "output_format": "json"
}
```

Модель і міркування виберіть серед доступних у вашому Codex. `task_thread`
зберігає контекст повторів однієї категорії й відокремлює його від наступної.
Для QA задайте `read-only`, критерії активного завдання та власні інструкції
перевірки. Якщо QA теж потребує дослідницького skill, підключіть його явно.

## Схема Flow

```text
Tasks Manager.NEXT → Research Executor → Task Reviewer → Result
        ↑                                               │
        ├────────────────────── TRUE ───────────────────┤
        └────────────────────── EXHAUSTED ───────────────┤
Research Executor ←──────────── FALSE ───────────────────┘

Tasks Manager.DONE → Підсумковий Executor → Підсумковий QA → Result
```

| Зв'язок | Мапінг |
| --- | --- |
| Tasks Manager.NEXT → Research Executor | `data.prompt → prompt` |
| Research Executor → Task Reviewer | `data → work` |
| Task Reviewer → Result | `data → review` |
| Result.FALSE → Research Executor | `data.retry_context → prompt` |
| Result.TRUE / EXHAUSTED → Tasks Manager | `data → input` |
| Tasks Manager.DONE → Підсумковий Executor | `data → input` |

За прямого підключення менеджера до виконавця встановіть
`Task Reviewer.criteria_node` у ID менеджера: тоді критерії відповідають
поточній категорії. Якщо між ними є Prompt Reviewer, можна використовувати
його уточнений промпт як еталон.

EXHAUSTED — необов'язкова політика продовження після невдачі. Якщо підключаєте
її, фінальний етап повинен прочитати статуси всіх завдань і показати провали
та неповне покриття. DONE означає завершення черги, а не приймання кожного звіту.

## Вимоги до кожного дослідження

- Використовуйте перевірені джерела: URL, автор/організація, дата публікації
  та дата перевірки. Для правил платформ починайте з офіційної документації.
- Відокремлюйте факти, досвід автора й власні висновки. Пояснюйте суперечності
  між джерелами та невизначеність.
- Для YouTube зберігайте назву, канал, URL, дату, корисні таймкоди й підставу
  висновку: відео, субтитри або лише опис. Не видавайте опис за перегляд відео.
- Показуйте релевантність до конкретного продукту, пріоритет, трудомісткість
  і спосіб вимірювання результату. Недоступні дані позначайте як прогалини.
- Ведіть журнал запитів і критерії завершення. «Вся інформація інтернету»
  не є перевірюваним критерієм; задайте теми, період, мови та мінімальне покриття.
- Контакти авторів беріть із публічних професійних сторінок. Підготовка списку
  не означає автоматичного надсилання листів, повідомлень або ключів гри.

QA має перевіряти відповідність вимогам, файли й джерела, а не лише довжину
звіту. Для TRUE потрібні узгоджені `verdict`, `score`, `issues` і `must_fix`.
`missing_requirement` є блокувальною категорією навіть із severity warning;
докладно — [контракт QA](../DOCUMENTATION.md#qa-та-повторні-спроби).

## Перевірка перед довгим запуском

Спочатку перевірте граф, доступність файлів інструкцій і роботу пошуку на
невеликому завданні. Імітація `FLOWAI_FAKE_CODEX=1` перевіряє маршрути, але
не доводить доступ до інтернету або якість дослідження. Під час нового збору
актуальних відомостей перевіряйте, чи налаштований кеш QA не повертає стару
оцінку незмінених локальних файлів.

Великі результати зберігайте на диску; передавайте між нодами ID завдання,
короткий підсумок, фактичні шляхи файлів і статус. Підсумковий етап повинен
прочитати прийняті звіти, звірити суперечності й сформувати план дій.
