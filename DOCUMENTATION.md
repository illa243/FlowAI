# Документація FlowAI

Версія пакета **0.4.0**, формат Flow **2**. Звірено з поточним кодом
**3 вересня 2026 року**. Точні поля JSON наведені у
[специфікації для AI](FLOWAI_NODE_GUIDE.md); історичні плани — в
[архіві](docs/README.md).

FlowAI — настільний редактор автоматизованих процесів із Codex-агентами.
Блоки виконують роботу, перевіряють результат і визначають наступний крок.
У програмі є **вісім типів блоків**. П’ять із них можуть викликати модель:
Prompt Reviewer, Task Executor, Task Reviewer, Calibration Stop і Work Reviewer.

## Встановлення та оновлення

Потрібні Windows, PowerShell і Python 3.10+ у `PATH`. Для роботи моделей
потрібні інтернет і доступ до Codex через профіль ChatGPT.

У папці завантаженого репозиторію виконайте:

```powershell
powershell -ExecutionPolicy Bypass -File .\install.ps1
```

Інсталятор створює `.venv`, установлює FlowAI із залежностями, додає ярлик
**FlowAI.lnk** у папку програми та меню «Пуск». Звичайний запуск:
**FlowAI.lnk** або **start-flowai.cmd**. Консоль для цих способів не потрібна.
Якщо `.venv` відсутня, CMD-скрипт викликає інсталятор.

Для запуску з діагностикою у PowerShell:

```powershell
.\.venv\Scripts\python.exe -m flowai
```

Для оновлення Git-копії закрийте програму зі збереженням роботи, отримайте
зміни та повторіть установлення:

```powershell
git pull --ff-only
powershell -ExecutionPolicy Bypass -File .\install.ps1
```

Якщо Git повідомляє про локальні зміни чи розбіжність гілок, спочатку
узгодьте їх. Інсталятор не є засобом резервного копіювання Flow-проєктів.
Номер версії в цьому посібнику відповідає `pyproject.toml`; дата документації
не означає створення нового релізу.

## Вхід і моделі

Натисніть **Увійти в ChatGPT**, завершіть авторизацію у браузері та дочекайтеся
оновлення профілю. **СКАСУВАТИ** припиняє поточну спробу входу. Натискання
авторизованого профілю дозволяє вийти після підтвердження.

```text
FlowAI → локальний Codex SDK / app-server → вибрана модель
```

FlowAI використовує збережений вхід Codex; окремого поля OpenAI API-ключа
немає. Моделі працюють у хмарі. Доступність моделі та ліміти визначає
підключений профіль, а не файл Flow.

Біля профілю показується найменший доступний залишок ліміту у відсотках.
Підказка містить доступні вікна лімітів і час скидання. Дані оновлюються під
час запуску, після входу та виконання Flow, а також кожні п’ять хвилин.

Поле **Модель** у Parameters редаговане. Використовуйте ідентифікатор, який
доступний вашому Codex; список у UI та довільний введений текст самі по собі
не гарантують доступу. Те саме стосується рівня міркування.

## Інтерфейс і панелі

### Верхня панель і меню

| Елемент | Дія |
| --- | --- |
| Settings | Назва Flow, папки й налаштування проєкту |
| Edit Flow | Редагування поточного Flow через AI |
| Run | Новий запуск або продовження збереженого прогресу |
| Pause / Resume | Пауза виконання / продовження |
| Stop | Переривання активного ходу зі збереженням прогресу |
| Files | Файли поточного запуску, згруповані за блоками й проходами |
| Stats | Статистика поточного або збережених запусків |
| Профіль | Вхід, ліміти, вихід |

**Файл** містить створення, відкриття та збереження Flow. **Редагування** —
скасування, повернення змін, видалення й показ усього графа. У **Запуск** є
керування виконанням і відновлення прогресу. **Довідка** відкриває папку логів
та вікно **Про FlowAI**.

### Показ і відновлення панелей

Меню **Вигляд** містить перемикачі **Проєкти**, **Ноди**, **Властивості**,
**Журнал виконання**. Для повернення проєктів у видиму нижню панель є команда
**Повернути панель проєктів униз**. Вона також прикріплює назад від’єднану
панель; список проєктів зберігається.

Панелі можна перетягувати до будь-якого краю або від’єднувати в окремі вікна.
Положення, розмір, прихований і плаваючий стан автоматично зберігаються
невдовзі після зміни. Реєстр проєктів зберігається окремо.

Списки проєктів і нод стають горизонтальними у широкій низькій панелі.
Для панелі зверху чи знизу вузький маркер праворуч змінює ширину; подвійний
клік повертає повну ширину. Зліва й справа працює звичайна межа з полотном.
У плаваючої панелі є системна кнопка розгортання.

Текст заголовків панелей проєктів, нод і журналу прихований для компактності.
Панель властивостей має заголовок **Parameters**.

### Полотно та Parameters

Виберіть блок або зв’язок, щоб редагувати його властивості. Велике текстове
поле можна розгорнути в окремий редактор; **Застосувати** повертає зміни,
**Скасувати** залишає попереднє значення. Некоректний JSON позначається
червоною рамкою й не замінює останню коректну конфігурацію.

Під час роботи блок показує етап, час проходу, модель і міркування. Ітерації
мають окремі таймери. Незмінні параметри активних нод блокуються; ліміти
TRUE/FALSE і очікування підтвердження Result можна змінювати під час роботи.

| Керування | Дія |
| --- | --- |
| `Ctrl+N`, `Ctrl+O`, `Ctrl+S` | Новий Flow, відкрити, зберегти |
| `Ctrl+Shift+S` | Зберегти як |
| `Ctrl+Z`, `Ctrl+Y` | Скасувати / повернути зміну поточного проєкту |
| `F2` | Перейменувати вибрану ноду або проєкт у списку |
| `Delete`, `Backspace` | Видалити вибрані елементи графа |
| Колесо миші | Масштаб полотна |
| Затиснута права кнопка миші | Переміщення полотна |
| Подвійний клік по зв’язку | Додати керовану точку вигину |

## Проєкти та файли

Кожне середовище має окремі граф, журнал, стани нод, checkpoint та історію
редагування. Сірий індикатор — ще не завантажений проєкт,
жовто-помаранчевий — завантажений у фоні, зелений — вибраний. Окрема іконка
показує виконання, непрочитаний результат, помилку або очікування відповіді.

Пошук фільтрує назви й шляхи. Контекстне меню дозволяє відкрити, перейменувати,
зберегти, показати у Провіднику, вивантажити або прибрати проєкт зі списку.
Прибирання зі списку не видаляє файл із диска. При відсутньому файлі запис
залишається, а програма повідомляє про неможливість його відкрити.

Після запуску список відновлюється, але проєкти завантажуються при виборі.
Тоді FlowAI також шукає збережений незавершений запуск. Перемикання між
проєктами не зупиняє активних Flow і не запускає їх заново.

### Одна тека на Flow

```text
my-flow/
├── my-flow.flowai.json
├── artifacts/       результати агентів
├── tools/           скрипти й допоміжні утиліти
├── reports/         окремі звіти
├── instructions/    локальні MD-інструкції, якщо потрібні
├── .flowai/runtime/ службові кеші, аудити й маніфести
└── runs/            журнали й checkpoint запусків
```

Для збереженого Flow робочою текою запису є папка самого `.flowai.json`.
Під час «Зберегти як» програма за потреби створює окрему однойменну теку.
Поля `workspace` та `additional_folders` у Flow і нодах можуть вказувати
додаткові джерела; вони не змінюють проєктну теку результатів.

Додаткові папки повинні існувати. Інструкції Runner визначають зовнішні
джерела як доступні для читання. Не налаштовуйте результат у папці вихідних
даних: використовуйте `artifacts/`. Старі абсолютні шляхи в керованих
Runner виходах можуть бути перенесені всередину проєкту; перевіряйте
фактичний шлях у результаті ноди.

### Доступ агента

| Режим | Призначення |
| --- | --- |
| `read-only` | Аналіз і QA без зміни файлів агентом |
| `workspace-write` | Створення й редагування файлів проєкту |
| `full-access` | Розширений доступ, якщо він потрібен зовнішнім інструментам |

Правило проєктної теки діє в інструкціях для всіх режимів; `full-access`
не є технічною ізоляцією файлової системи. Перед його запуском UI показує
окреме попередження. Журнали й checkpoint записує сама програма, зокрема й
для read-only QA. Передавання вердикту між нодами не потребує файлового запису
з боку агента.

## Створення Flow і GrillMe

**Файл → Новий** пропонує стартову схему, порожній Flow або складання з AI.
У AI-режимі опишіть очікуваний результат, папки та обмеження. GrillMe ставить
уточнювальні питання перед побудовою. Composer використовує MCP FlowAI для
створення й валідації графа.

**Edit Flow** працює з конкретним поточним файлом через чернетку. Перед
передаванням його AI програма зберігає поточні зміни.

Стартова схема:

```text
Entry → Prompt Reviewer → Executor → Task Reviewer → Result
                            ↑                         │
                            └──────── FALSE ──────────┘
```

У ній також є Work Reviewer без зв’язків. Для кількох задач початковим блоком
може бути Tasks Manager без окремого Entry. Приклад:
[review_loop.flowai.json](examples/review_loop.flowai.json).

Перед новим Run можна пройти GrillMe: відповісти на питання, переглянути
запропоновані зміни й застосувати їх або повернутися до редагування. Зміни
постановки задачі входять до історії редагування; зберігайте їх у файл окремо.

## Типи блоків

### Entry prompt

Одноразове джерело `text`, початкового `json` і `attachments`. Для виконавця
із `prompt_source: "input"` передавайте `text → prompt`, для цілого пакета —
`data → input`. Підтримувані зображення надсилаються як локальні зображення,
інші вкладення — як шляхи для інструментів агента.

### Tasks Manager

Видає одне активне завдання через `NEXT`; `DONE` означає завершення черги.
Кожне завдання має стабільний ID, промпт і вкладення. В UI можна додавати й
прибирати секції; порожні промпти не проходять валідацію.

Типовий маршрут: `NEXT → Executor → QA → Result`, `TRUE → Tasks Manager`,
`FALSE → Executor`. Додатково `EXHAUSTED → Tasks Manager` дозволяє зафіксувати
невдачу й продовжити чергу. Для фінального підсумку підключіть `DONE`.

Ефективний TRUE-ліміт Result для менеджера враховує кількість завдань.
Передача `data.prompt → prompt` підходить прямому виконавцю; `data → input`
передає повний пакет у Prompt Reviewer. Докладні поля стану та правила
переходу наведені у [специфікації](FLOWAI_NODE_GUIDE.md#tasks-manager-tasks_manager).

### Prompt Reviewer

Уточнює постановку задачі, враховуючи подальші блоки. Повертає JSON із
`improved_prompt` і `notes`. `improved_prompt` також стає вихідним `text`.
Доступні `{{entry_prompt}}` та `{{flow_chain}}`; за замовчуванням опис ланцюга
компактний, а не повна копія конфігурації кожної ноди.

### Task Executor

Виконує задачу й повертає текст або JSON за налаштуванням. Типово читає
вхід `prompt` і має `workspace-write`. На повторі отримує `retry_context`
із зауваженнями та даними попереднього результату.

### Task Reviewer

Перевіряє роботу за критеріями. **Блок-еталон** визначає джерело `criteria`;
для черги можна явно вибрати Tasks Manager, щоб перевіряти активне завдання.
Типовий доступ — `read-only`. Висновок обов’язково проходить перевірку
узгодженості перед передаванням у Result.

### Result

Обирає `TRUE` чи `FALSE`, рахує проходи та за потреби чекає підтвердження.
`template` і `save_path` формують та зберігають прийнятий результат на TRUE.
Типові значення: `true_limit: 1`, `false_limit: 3`, `task_attempt_limit: 2`.

Третій вихід `EXHAUSTED` стосується бюджету активного завдання Tasks Manager.
За підключеного виходу невдача фіксується, і черга може продовжитися. Без
цього маршруту доступний діалог додавання спроб. Підсумковий запуск із
невдалими завданнями позначається як виконаний із провалами.

Режими підтвердження: `standard`, `plan_approval`, `variant_selection`,
`asset_approval`. У складному Flow проміжні Result мають
`final_task_result: false`, щоб вибір концепту не завершив усе завдання.
Остаточний Result створює запис про прийнятий перехід.

### Calibration Stop

Ставиться між Result.FALSE та Executor, аналізує невдалий прохід і пропонує
правки інструкцій. `false_threshold` задає поріг, `auto_skip` пропускає
аналіз без виклику моделі. Застосування змін потребує рішення у вікні
калібрації. Повний опис і відмінності кнопок —
[Калібрація Flow](guides/calibration.md).

### Work Reviewer

Бічний блок без портів; у Flow допускається один. Записує протокол усіх або
вибраних нод, а після завершення аналізує його. Налаштування:
`monitor_all`, `monitored_nodes`, `report_path`. Це спостерігач процесу;
він не замінює Task Reviewer на маршруті приймання результату.

## Параметри агентів

| Поле | Значення |
| --- | --- |
| `model`, `reasoning_effort` | Модель і підтримуваний нею рівень міркування |
| `instructions` | Постійні інструкції ролі |
| `instruction_files` | Файли `.md` / `.markdown`, прочитані як інструкції |
| `prompt_source` | `template` або `input` |
| `prompt` | Шаблон запиту |
| `output_format`, `output_schema` | Текст або JSON і очікувана структура |
| `sandbox` | Рівень доступу |
| `attachments` | Постійні вкладення ноди |
| `skills` | Закріплені skills із назвами й локальними шляхами |
| `workspace`, `additional_folders` | Додаткові джерела даних |
| `retries` | Повтори технічних помилок |
| `memory` | `thread`, `fresh` або `task_thread` |

`thread` продовжує тред блока; `fresh` створює новий для кожного виклику;
`task_thread` ізолює контекст за ID завдання, зберігаючи історію його повторів.
Після перевищення `context_soft_limit` наступний хід починається у чистому
контексті. Ці механізми не скасовують файлові результати попередньої роботи.

Повтор технічної помилки (`retries`), виправлення структури QA
(`qa_correction_attempts`) та доопрацювання через Result.FALSE — різні механізми.
Параметр `timeout_seconds` вилучено зі схеми: він не встановлює часовий ліміт
агента. Тривалі операції контролюються зупинкою та, за налаштуванням,
лімітами ітерацій і відсутності покращення.

Текстові ноди зберігають відповідь у `data.response`, не підміняючи її випадковим
JSON усередині тексту. Для структурованих нод Runner розбирає JSON. Великі входи
можуть скорочуватися для транспорту; докази слід зберігати у файлах і передавати
посиланнями. Точні додаткові поля — у [довіднику](FLOWAI_NODE_GUIDE.md#спільні-параметри-агентів).

## З’єднання та шаблони

Потягніть вихідний порт до входу або послідовно клацніть обидва. У Parameters
зв’язку налаштуйте мапінг. Подвійний клік додає точку вигину; вона змінює лише
геометрію, а не порядок роботи.

| Поле зв’язку | Приклад |
| --- | --- |
| `source_port` | `out`, `next`, `done`, `true`, `false`, `exhausted` |
| `source_path` | `text`, `data`, `data.improved_prompt`, `data.retry_context`, `$` |
| `target_variable` | `prompt`, `work`, `review`, `criteria`, `input` |
| `condition` | `source.status == "success"` |
| `transform` | Шаблон із `{{value}}` |

Практичні мапінги: `Executor.data → QA.work`, `QA.data → Result.review`,
`Result.false:data.retry_context → Executor.prompt`. Якщо QA перевіряє результат,
не прокладайте паралельного переходу виконавця до наступного етапу в обхід QA.

Шаблони підтримують `{{inputs}}`, `{{criteria}}`, `{{work}}`, іменовані входи й
вкладені шляхи на кшталт `{{plan.steps}}`. Доступні також дані Workflow,
підсумок GrillMe й номер ітерації. Умови обчислює обмежений інтерпретатор
виразів у `flowai/templating.py`, а не довільний Python-код.

Runner виконує чергу послідовно всередині одного Flow. Незалежні вхідні пакети
можуть запустити ту саму ноду окремими проходами; зв’язок не є автоматичним
бар’єром очікування всіх гілок. Зворотні маршрути проходять через Result.

## QA та повторні спроби

### Коректний вердикт

Новий Task Reviewer типово використовує `strict_review_contract: true`,
`pass_threshold: 80`, `qa_correction_attempts: 1`. Приклад прийнятого результату:

```json
{
  "verdict": true,
  "score": 95,
  "reason": "Обов’язкові вимоги перевірено, джерела підтверджують висновки",
  "must_fix": [],
  "issues": [],
  "checks": [{"check_id": "sources", "status": "pass"}]
}
```

`verdict` — boolean, `score` — ціле 0–100. TRUE потребує оцінки не нижче
порога, порожнього `must_fix`, відсутності failed checks і блокувальних issues.
FALSE повинен містити issue або `system_error`; старі `reason`/`must_fix`
можуть нормалізуватися у структуровані issues для сумісності.

Issue блокує приймання, якщо:

- `severity` — `blocking`, `blocker`, `critical` або `error`; **або**
- `category` — `missing_requirement`, `technical_blocker` або `visual_mismatch`.

Отже, `category: "missing_requirement"` блокує результат навіть із
`severity: "warning"`. Невиконану вимогу треба повернути на доопрацювання.
Необов’язкову пораду, яка не є порушенням вимог, можна описати в `reason`.

### Некоректна відповідь QA

Runner спочатку просить QA виправити структуру й узгодженість JSON у межах
`qa_correction_attempts`. Якщо це не допомагає, зберігає паузу
`invalid_qa_contract`. У відкритому вікні видно помилки та фрагмент відповіді.

**Повторити QA** повертає поточну QA-ноду до виконання із збереженими входами
та поясненням помилки; можна дописати власну інструкцію. Це не є прийманням
попереднього вердикту. Закриття цього вікна через X/Esc зберігає паузу;
**Зупинити Flow** залишає прогрес доступним для продовження.

### Захист повторних проходів

За ввімкнених відповідних параметрів FlowAI формує `retry_context` із
зауваженнями, стабільними ID дефектів, невдалими перевірками та файлами, які
дозволено змінювати. Прийняті файли можуть захищатися SHA-256.

`retry_guard_enabled` зупиняє автоматичні повтори за повторними дефектами або
регресією. `operation_intent_required` перевіряє план ітеративної операції;
`operation_policy` задає бюджет і відсутність покращення. Кеші prompt/QA та
детерміновані перевірки працюють лише за відповідної конфігурації нод.

Для UI-сценаріїв існують контракти чотирьох PNG-варіантів, вибір концептів і
перевірка PSD через Photoshop. [UI-шаблон](examples/game_ui_workflow.flowai.json)
потребує власних референсів, skills, налаштованих шляхів і Photoshop.

## Пауза, зупинка та відновлення

| Дія | Поведінка |
| --- | --- |
| Pause | Запитує паузу; активна робота може завершуватися до точки очікування |
| Resume | Продовжує ручну паузу |
| Stop | Перериває активний turn, повертає незавершену ноду в чергу та зберігає checkpoint |
| Run за наявності прогресу | Дозволяє продовжити збережений запуск або почати новий |
| Відновити прогрес з останнього журналу | Відбудовує доступний стан із журналу запуску |
| Відкинути збережений прогрес | Прибирає стан продовження окремою дією; артефакти залишаються |

Checkpoint містить чергу, входи, результати, стани завдань, лічильники та ID
тредів. Він записується на диск на межах виконання. Після перезапуску виберіть
проєкт, щоб FlowAI відновив очікування або запропонував продовження.
Завершені ноди не потрібно повторювати для звичайного продовження checkpoint.

Result може чекати підтвердження, додаткових спроб або рішення щодо повторних
дефектів. Закриття через X/Esc вікна підтвердження Result або Retry Attention
залишає Flow на паузі. Діалог ліміту та Calibration Stop мають власну поведінку:
зокрема **Зупинити Flow** або відхилення у Calibration Stop скасовує запуск і
прибирає його checkpoint. Для збереження калібраційної паузи не завершуйте її
як скасування; дивіться [опис калібрації](guides/calibration.md).

Під час закриття програми з активними Flow з’являється запит на зупинку зі
збереженням. Сон або блокування Windows переводить роботу в кероване
очікування; після пробудження/розблокування вона продовжується. Це не відновлює
зовнішні служби, якщо вони розірвали з’єднання чи відхилили запит.

## Skills і Deep research

У полі **Скіли** можна закріпити локальні skills; вони передаються SDK як
`SkillInput`. Локальний каталог FlowAI сканує `%USERPROFILE%\.codex\skills`
і вкладені системні skills. Наявність plugin у Codex не гарантує, що його
skill з кешу plugin автоматично з’явиться в цьому списку.

Альтернатива — **MD-інструкції** (`instruction_files`). Вкажіть наявний
`SKILL.md` або проєктну копію інструкцій. Відносні шляхи обчислюються від
проєктної теки. Додайте також потрібні файли, на які посилається skill.
MD-інструкції не встановлюють інструменти, plugin чи доступ до сервісів.

У FlowAI немає окремого типу ноди або перемикача Deep research. Дослідницький
процес можна скласти зі звичайних Executor/QA, підключивши відповідні
інструкції й перевіривши доступні пошукові інструменти Codex. Це не окрема
інтеграція API Deep Research. Дивіться
[покроковий довідник](guides/deep-research.md).

## MCP-сервер

FlowAI постачає stdio-сервер для складання й редагування Flow:

```powershell
.\.venv\Scripts\python.exe -m flowai.mcp
```

Приклад налаштувань для MCP-клієнта з JSON-конфігурацією
(замініть `C:/tools/FlowAI` власним шляхом):

```json
{
  "mcpServers": {
    "flowai": {
      "command": "C:/tools/FlowAI/.venv/Scripts/python.exe",
      "args": ["-m", "flowai.mcp"]
    }
  }
}
```

Клієнти можуть мати інший формат конфігурації; команда та аргументи лишаються
тими самими. Сервер не є HTTP-службою і не має вебсторінки керування.

Основні групи інструментів: опис типів нод; створення/завантаження чернетки;
редагування нод, завдань і зв’язків; автоматичне компонування; валідація й
збереження; пошук Flow; читання довідників. `save_flow` валідує граф перед
записом. Сервер не запускає дослідження: виконання запускається у FlowAI.

Файли `guides/*.md` автоматично доступні через `list_guides` і `read_guide`.
Для точного поточного переліку викличте MCP discovery або прочитайте
`flowai/mcp/server.py`.

## Журнали, файли та статистика

```text
runs/<час-запуску>/
├── flowai-run.json          події, результати й статус запуску
├── flowai-checkpoint.json   стан продовження, поки він потрібен
├── work-review.md           якщо є Work Reviewer
├── work-review-report.md    аналіз Work Reviewer
└── calibration.json         якщо виконувалася калібрація
```

Звичайне продовження використовує ту саму папку запуску. Статуси включають
успіх, невдачу, зупинку та `paused_attention`. Checkpoint і журнал не є
резервною копією всіх артефактів.

**Files** групує проміжні й фінальні файли за нодою та проходом. Вхідні
вкладення не повинні показуватися як створені результати. Відсутні на диску
файли лишаються в історії з позначкою недоступності.

**Stats** показує проходи, тривалість і доступні дані використання токенів та
контексту для поточного або збережених запусків. Відсутні дані SDK не означають
нульове використання.

Екранний журнал окремий для кожного проєкту. Повні промпти й дані залишаються
у машинному журналі/протоколі, тоді як UI показує стислий потік активності.
**Очистити** прибирає екранний текст і не видаляє збережені журнали.

Діагностика програми: `%LOCALAPPDATA%\FlowAI\logs\flowai.log` і `crash.log`.
Відкриття — **Довідка → Відкрити папку логів**. Є ротація та дампи потоків
при зависанні. Windows-сповіщення про результат або увагу дозволяють повернутися
до відповідного проєкту й блока.

Журнали містять промпти, відповіді й локальні шляхи. Перевіряйте їх перед
публікацією. Облікові дані Codex не зберігаються у `.flowai.json`.

## Типові проблеми

| Симптом | Що перевірити |
| --- | --- |
| Зникла нижня панель проєктів | Вигляд → Повернути панель проєктів униз; також очистіть пошук |
| `invalid_qa_contract` | Відкрийте проєкт/ноду, прочитайте помилки, натисніть Повторити QA |
| «Невідомий тип запиту: invalid_qa_contract» | Оновіть код і перезапустіть FlowAI; старий процес не підхоплює виправлення автоматично |
| Кнопка знову пропонує вхід | Повторіть авторизацію, перевірте доступ і ліміти профілю |
| Не знайдено файл інструкцій / папку | Виправте локальний шлях; відносні шляхи рахуються від проєкту |
| Result не отримав вердикт | Перевірте зв’язок `QA.data → Result.review` |
| Наступна нода не запускається | Перевірте порт, умову переходу, `source_path`, назву вхідної змінної й результат попередника |
| Повторюється той самий дефект | Перевірте зауваження, бюджет спроб і Retry Attention; за потреби застосуйте калібрацію |
| Немає Deep research у списку skills | Перевірте локальний каталог або підключіть наявні MD-інструкції; окремого перемикача немає |
| UI-шаблон просить референси / Photoshop | Замініть локальні шляхи автора та налаштуйте необхідні зовнішні ресурси |
| Stop ще завершується | Дочекайтеся переривання turn та збереження checkpoint; повторний запуск заблоковано до завершення зупинки |
| Перевищено ліміт кроків | Перевірте граф і ліміти Result; типовий загальний запобіжник Runner — 200 кроків |
| Flow формату 1 не відкривається | Створіть схему формату 2; автоматичного перенесення старого набору нод немає |

## Поточні обмеження

- Робота моделей потребує інтернету та доступу профілю Codex.
- Незалежні гілки одного Flow виконуються послідовно; глобальної черги
  чи ліміту одночасних фонових Flow немає.
- Підтримується формат Flow 2; автоматичної конвертації формату 1 немає.
- Окремого API-конектора Deep Research і автоматичного підключення всіх
  plugin-skills Codex у локальний каталог FlowAI немає.
- Зовнішні інструменти, референси, Photoshop і локальні skills потрібно
  налаштовувати окремо; їх не створює сам факт завантаження шаблону.
- Відновлення залежить від збереженого checkpoint/журналу та доступних файлів.
  Воно не повертає видалені артефакти або зовнішній стан сервісів.
- Окремого менеджера секретів немає. `full-access` потребує довіри до
  інструкцій та інструментів Flow.
