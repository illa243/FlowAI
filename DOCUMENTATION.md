# Документація FlowAI

Версія програми: **0.3.0**<br>
Формат Flow: **2**

FlowAI — локальна настільна програма для створення автоматичних Workflow з
Codex-агентами. Схема складається з блоків і з’єднань: кожен блок виконує окрему
операцію, а з’єднання визначають, які дані отримає наступний крок.

Версія 0.3 замінила універсальні ноди на шість спеціалізованих блоків під один
робочий процес: **промпт → покращення → виконання → перевірка → приймання або
переробка**. Блок Result розгалужує потік на True/False, тому Flow тепер може
містити цикл — виконавець переробляє результат, доки рев’ювер його не прийме.

Файли попереднього формату (версія 1) не відкриваються: набір блоків змінився
повністю, тож такі Flow потрібно створити заново.

FlowAI не потребує OpenAI API-ключа. Програма використовує вхід у ChatGPT,
збережений офіційним Codex SDK. Самі GPT-моделі не запускаються локально: для їхньої
роботи потрібні інтернет, активний сеанс ChatGPT і доступний ліміт Codex у тарифі.

## Системні вимоги

- Windows із PowerShell.
- Python 3.10 або новіший, доступний через команду `python`.
- Інтернет-з’єднання для авторизації та роботи GPT-моделей.
- Обліковий запис ChatGPT із доступом до Codex.

Основні Python-залежності з `pyproject.toml` встановлюються автоматично:

- `PySide6>=6.9,<7` — графічний інтерфейс;
- `openai-codex>=0.147,<0.148` — локальне керування Codex.

## Встановлення і запуск

### Перше встановлення

1. Відкрийте PowerShell у папці `FlowAI`.
2. Виконайте:

   ```powershell
   powershell -ExecutionPolicy Bypass -File .\install.ps1
   ```

Скрипт створить ізольоване середовище `.venv` і встановить FlowAI разом із
залежностями.

### Звичайний запуск

Запустіть подвійним кліком:

```text
start-flowai.cmd
```

Альтернативний запуск із PowerShell:

```powershell
.\.venv\Scripts\python.exe -m flowai
```

Якщо середовище `.venv` відсутнє, `start-flowai.cmd` автоматично викличе
`install.ps1`.

## Вхід у ChatGPT

1. Натисніть **Увійти в ChatGPT** у правій частині панелі інструментів.
2. FlowAI відкриє браузер зі сторінкою авторизації.
3. Завершіть вхід у браузері.
4. FlowAI автоматично отримає результат і замінить кнопку входу аватаром,
   нікнеймом та відсотком доступного ліміту.

Поки триває авторизація, у вікні FlowAI доступна лише кнопка **СКАСУВАТИ**. Вона
припиняє поточну спробу входу.

### Профіль і ліміти

Після входу кнопка профілю має вигляд:

```text
[аватар] nickname · NN%
```

`NN%` — найменший залишок серед усіх активних вікон ліміту Codex. Він
обчислюється як `100 − використаний відсоток`. Наведіть курсор на профіль, щоб
побачити:

- пошту і загальний доступний залишок;
- тариф ChatGPT;
- окремі ліміти моделей;
- тривалість кожного вікна;
- дату й час наступного скидання.

FlowAI оновлює дані під час запуску програми, після авторизації, після виконання
Flow і кожні п’ять хвилин.

Щоб вийти, натисніть кнопку профілю та підтвердьте дію. Вихід завершує спільну
локальну сесію Codex на цьому комп’ютері.

## Як FlowAI працює без API-ключа

Фраза **«без API»** у FlowAI означає **без власного OpenAI API-ключа та без
окремої оплати за використання API Platform**. Під час входу через ChatGPT Codex
зберігає локальну авторизовану сесію. FlowAI запускає офіційний Python Codex SDK,
а SDK використовує цю сесію та доступ Codex у тарифі ChatGPT користувача.

Схема роботи:

```text
FlowAI → локальний Codex SDK/app-server → сервери OpenAI → вибрана GPT-модель
```

FlowAI не читає API-ключ із налаштувань і не записує облікові дані у файл
`.flowai.json`. Водночас це не локальний і не офлайн-запуск GPT: запит моделі
обробляється на серверах OpenAI, тому потрібні інтернет, активний вхід у ChatGPT,
доступ до вибраної моделі та невичерпаний ліміт Codex.

Використання агентів враховується у лімітах Codex підключеного ChatGPT-профілю.
Саме залишок цих лімітів FlowAI показує біля імені користувача.

## Інтерфейс програми

Головне вікно має шість основних частин.

### Верхня панель

- **⚙ Settings** — змінити назву та спільну робочу папку Flow.
- **Run** — зелена кнопка перевірки й запуску схеми; під час виконання вибраного
  проєкту вона неактивна й сіра.
- **Stop** — червона кнопка негайної зупинки всіх генерацій вибраного проєкту;
  коли проєкт не виконується, вона неактивна й сіра.
- **Files** — відкрити впорядкований список проміжних і фінальних файлів
  поточного запуску вибраного проєкту. Кнопка доступна також під час виконання.
- **Профіль** — вхід, інформація про ліміти та вихід із ChatGPT.

Команди **Новий**, **Відкрити** та **Зберегти** прибрані з верхньої панелі, але
залишаються у меню **Файл** і доступні через `Ctrl+N`, `Ctrl+O` та `Ctrl+S`.

### Панель «Ноди»

Ця dock-панель містить лише кнопки додавання всіх шести типів блоків. Новий блок
з’являється у центрі
поточної області полотна. У високій вузькій панелі кнопки розміщуються вертикально,
а у широкій низькій — горизонтально. Панель не містить постійних текстових
підказок і може вільно розтягуватися по ширині після прикріплення до будь-якого
краю вікна.

У всіх dock-панелей видимий текст заголовка прихований, а службова смуга зменшена.
Смуга залишається доступною для перетягування та прикріплення панелі; призначення
панелі доступне у спливаючій підказці.

Після від'єднання dock-панель стає модульним вікном. У його системній смузі біля
помітної кнопки закриття є кнопка розгортання: вона автоматично збільшує панель на
весь екран, а повторне натискання повертає попередній розмір. Кнопка закриття має
контрастний червоний вигляд замість малопомітного сірого.

У панелі, прикріпленої зверху або знизу, праворуч показується вузький вертикальний
маркер. Перетягуйте його вліво або вправо, щоб незалежно змінити ширину панелі,
а не лише її висоту. Подвійний клік повертає повну ширину. Для панелей зліва та
справа ширина, як і раніше, змінюється перетягуванням звичайної межі з полотном.

### Панель «Робочі середовища»

Показує збережені Flow-проєкти, їхній стан завантаження та виконання. Між
середовищами можна перемикатися, не зупиняючи фонові Flow. Детальні правила станів
описані в наступному розділі. Панель можна прикріпити зверху, знизу або збоку та
змінювати її ширину перетягуванням межі dock-області.

### Полотно

На полотні можна:

- перетягувати блоки мишею;
- виділяти один або кілька блоків рамкою;
- створювати з’єднання перетягуванням між круглими портами;
- виділяти лінії з’єднань;
- змінювати масштаб колесом миші.

У шапці кожного блоку праворуч від назви показані перші шість символів його
ідентифікатора, наприклад `7f3a9c`. Саме за цим коротким id блок можна знайти у
протоколі роботи та вибрати у списках Інспектора.

Для активного блока після короткого id також показується номер етапу у форматі
`1/6`. Під назвою моделі видно вибраний тип **Міркування**, а внизу блока — назва
поточного етапу з легким пульсуванням.

Більшість блоків має один вхідний і один вихідний порт. Винятки:

- **Result** має два вихідні порти: зелений `TRUE` зверху і червоний `FALSE`
  знизу. Біля кожного показано, скільки разів гілку вже пройдено з дозволеного
  ліміту, наприклад `FALSE 2/3`.
- **Work Reviewer** не має портів узагалі — він не бере участі в маршруті.

Крапка внизу блоку показує його стан:

- `idle` — ще не запускався;
- `running` — виконується;
- `success` — виконаний успішно;
- `failed` — завершився помилкою;
- `waiting` — очікує на відповідь користувача.

Праворуч від статусу кожного блока показується **Час**. Поки блок працює, значення
оновлюється в реальному часі, а рамка й фон м’яко пульсують зеленим. Після
завершення пульсування припиняється, а фактична тривалість залишається на блоці.
Якщо блок запускається повторно, під попереднім часом з’являється новий таймер,
який знову рахує від нуля. Час різних проходів не додається. Новий запуск Flow
очищає список таймерів поточної сесії.

Блок, який чекає на рішення користувача, блимає жовтою рамкою. Клік по ньому
відкриває відповідне вікно.

### Інспектор

Права панель має заголовок **Parameters** і показує лише редаговані властивості
вибраної ноди або з’єднання.
Коли нічого не вибрано, вона порожня; окремих заголовків, довідкового тексту,
типу та ID тут немає. Зміни застосовуються до Flow одразу, але для запису на диск
потрібно зберегти проєкт.

В агентських нодах натискання на напис **Модель** або на текстову частину поля
відкриває випадаючий список. Поле залишається редагованим, тому можна вибрати
готовий варіант або ввести іншу сумісну назву моделі вручну.

Кожне велике багаторядкове поле має невелику кнопку розгортання у правому
верхньому куті. Вона відкриває окремий максимізований редактор для зручної роботи
з довгим текстом. Кнопка **Застосувати** переносить змінений текст назад у ноду й
оновлює її конфігурацію; **Скасувати** закриває редактор без змін. Функція працює
для вхідного промпту, початкового JSON, постійних інструкцій, промпту агента,
JSON-схеми, шаблону результату та перетворення зв’язку.

Колесо миші у Parameters не змінює значення списків і числових полів. Під час
роботи ноди поля, які не можна безпечно змінити посеред запиту, блокуються. Для
активного Result доступними лишаються ліміти TRUE/FALSE та прапорець очікування:
їхні зміни одразу передаються запущеному Runner.

У списках вкладень зображення показуються зменшеними мініатюрами. Лівий клік
відкриває картинку на весь екран. Для текстових та інших форматів показується лише
назва файла. Контекстне меню правої кнопки миші дозволяє відкрити розташування у
Провіднику, скопіювати повний шлях або видалити вкладення зі списку; сам файл на
диску при цьому не видаляється.

Некоректний JSON у полі налаштувань позначається червоною рамкою і не замінює
останнє коректне значення.

### Журнал виконання

Нижня панель показує:

- початок і завершення запуску;
- сформовані промпти та постійні інструкції;
- результат і тривалість кожного блоку;
- повторні спроби, переробки та помилки;
- повідомлення блоку Work Reviewer із шляхом до готового звіту.

Повідомлення ноди мають формат `короткий id: повідомлення` та колір цієї ноди.
Нормалізовані кроки агента виводяться під час виконання, а виявлені шляхи
створених файлів підкреслюються, щоб результат було легко знайти у журналі.

Кнопка **Files** відкриває окреме вікно, яке оновлюється під час роботи. Групи
показуються в порядку завершення нод. Заголовок групи містить назву ноди, повний
ID і номер проходу; нижче розміщені **Проміжні файли**, а останньою секцією —
**Результат**. Назва, шлях і секції мають колір ноди. Вхідні вкладення не
потрапляють до списку як згенеровані файли. Подвійний клік відкриває наявний файл
у стандартній програмі, а видалений проміжний файл залишається в історії з
позначкою про недоступність. Історія окрема для кожного робочого середовища та
очищається на початку нового запуску, але не при продовженні після втручання.

Кнопка **Очистити** прибирає текст лише з інтерфейсу. Уже збережені журнали запусків
не видаляються. Окремого заголовка всередині панелі немає.

### Збереження лояута і шляхів

FlowAI запам’ятовує розташування елементів інтерфейсу в локальних налаштуваннях:

- розмір і позицію вікна, у тому числі розгорнутий стан;
- до якого краю прикріплена кожна панель, її розмір, плаваючий чи прихований стан;
- окремо встановлену ширину панелей, прикріплених зверху або знизу;
- папку, з якої востаннє відкривали або зберігали проєкт.

Під час наступного запуску вікно відновлюється в тому ж вигляді, а діалоги
**Відкрити** і **Зберегти як…** стартують з останньої використаної папки.
Зміни лояута записуються автоматично через коротку затримку після переміщення,
прикріплення, від’єднання, приховування або зміни розміру панелі. Тому останнє
положення вже не залежить лише від успішного завершення `closeEvent` і не губиться,
якщо процес пізніше аварійно завершується. Під час автоматичних тестів
використовується окреме тимчасове сховище налаштувань, тож тести не перезаписують
користувацький лояут у реєстрі Windows.

## Панель робочих середовищ

FlowAI підтримує список робочих середовищ у лівій боковій панелі. Одне робоче
середовище — це завантажений Flow-проєкт разом із його полотном, журналом,
поточним запуском, станами нод і незбереженими змінами.

Між середовищами можна перемикатися, не зупиняючи Flow, які виконуються у фоні.

### Загальний вигляд панелі

Панель розміщується ліворуч від полотна. Вона містить:

- кнопку **＋ Додати Flow**;
- пошук за назвою проєкту;
- прокручуваний список середовищ.

Для компактності окремий заголовок, пояснювальний текст і рядок загальної
статистики не показуються. Стани залишаються видимими безпосередньо на картках.

Орієнтація списку адаптивна: якщо доступна область ширша за свою висоту, картки
середовищ розміщуються горизонтально з прокруткою зліва направо. В інших випадках
вони розміщуються вертикально.

При першому запуску список видимий і клікабельний, але жодне середовище не вибране.
Усі елементи мають нейтральний сірий стан. У центрі вікна показується підказка:

```text
Виберіть робоче середовище або додайте новий Flow
```

Слово «неактивний» у цьому контексті означає «ще не завантажений», а не
«заблокований для натискання».

### Вигляд елемента списку

Кожне середовище представлене прямокутником із заокругленими кутами:

```text
│  Назва проєкту                              ◉
│  Необов’язковий короткий статус
```

Елемент складається з:

1. вертикальної кольорової лінії зліва;
2. назви Flow-проєкту;
3. необов’язкового короткого тексту стану;
4. іконки стану справа;
5. підказки з повним шляхом до файлу, станом запуску та часом останньої активності.

Рекомендовані параметри оформлення:

- радіус кутів — 8–10 px;
- товщина лінії — 4 px;
- висота елемента — щонайменше 48 px;
- назва обрізається через `…`, але повністю показується у підказці;
- активний елемент має трохи світліший фон і видиму рамку фокуса.

### Колір лінії

Колір лінії описує стан завантаження та вибору, а не результат виконання:

| Колір | Стан | Значення |
| --- | --- | --- |
| Сірий `#64748B` | Неактивний | Flow відомий програмі, але ще не завантажений у пам’ять |
| Жовто-помаранчевий `#F59E0B` | Завантажений | Flow відкритий у пам’яті, але користувач зараз працює в іншому середовищі |
| Зелений `#22C55E` | Вибраний | Це поточне середовище, його полотно, Інспектор і журнал показані в головній області |

Жовтий та оранжевий у цій специфікації є одним станом `amber`. Це усуває
неоднозначність між двома близькими кольорами.

Якщо вибраний Flow виконується, лінія залишається зеленою, а запуск показує іконка
завантаження. Якщо Flow працює у фоні, його лінія залишається жовто-помаранчевою,
а справа також показується іконка завантаження.

### Іконки стану

Іконка справа описує стан виконання незалежно від кольору лінії:

| Іконка | Внутрішній стан | Коли показувати |
| --- | --- | --- |
| Анімоване коло завантаження | `running` | Flow зараз виконується |
| Велика крапка | `completed_unread` | Flow завершився, поки користувач був в іншому середовищі |
| Трикутник зі знаком оклику | `needs_attention` | Flow призупинений і потребує відповіді, вибору або підтвердження користувача |
| Червоний хрестик | `failed` | Flow завершився помилкою |
| Іконка паузи | `paused` | Зарезервований стан; окремої команди ручної паузи в 0.3.0 ще немає |
| Без іконки | `idle` або `completed_seen` | Flow не запускався або його успішний результат уже переглянуто |

Після переходу до середовища з `completed_unread` велика крапка зникає, коли
користувач побачив фінальне повідомлення або журнал. Значок помилки чи втручання не
слід прибирати простим відкриттям — він зникає лише після виправлення помилки або
надання потрібної відповіді.

Колір не повинен бути єдиним способом передавання стану. Для доступності кожен
індикатор має мати текстову підказку, наприклад **Виконується**, **Завершено — є
непрочитаний результат** або **Очікує на вашу відповідь**.

### Правила перемикання

1. Клік по сірому елементу завантажує файл Flow і робить середовище вибраним.
2. Попереднє вибране середовище залишається в пам’яті та отримує
   жовто-помаранчеву лінію.
3. Нове вибране середовище отримує зелену лінію.
4. Його полотно, Інспектор, виділений елемент і журнал відновлюються в тому самому
   стані.
5. Flow, що вже працюють, продовжують виконання у фоні.
6. Завершення фонового Flow встановлює `completed_unread` і показує велику крапку.
7. Вичерпаний ліміт гілки Result встановлює `needs_attention` і показує трикутник.
8. Повернення до середовища не повинно автоматично перезапускати Flow.

Перемикання не повинно змішувати:

- виділені ноди різних проєктів;
- поточний масштаб і позицію полотна;
- журнали запусків;
- журнали та результати запуску;
- незбережені зміни;
- стани **Stop**, **Run** та інших кнопок.

### Переходи між станами

```text
Неактивний
    │ клік
    ▼
Завантажений + Вибраний
    │ запуск
    ▼
Виконується
    ├── успіх у вибраному середовищі ──► Завершено, переглянуто
    ├── успіх у фоновому середовищі ───► Завершено, непрочитано
    ├── запит до користувача ──────────► Потребує втручання
    ├── помилка ───────────────────────► Помилка
    └── ручна зупинка ─────────────────► Зупинено
```

Стан кольорової лінії та стан іконки необхідно зберігати окремо. Наприклад,
середовище може бути одночасно `loaded`, `running` і `not_selected`.

### Дії з робочим середовищем

Контекстне меню елемента містить:

- **Відкрити**;
- **Перейменувати**;
- **Зберегти**;
- **Зберегти як…**;
- **Показати у Провіднику**;
- **Вивантажити з пам’яті**;
- **Прибрати зі списку**.

Команда **Прибрати зі списку** не повинна видаляти `.flowai.json` із диска. Для
фізичного видалення файла потрібна окрема дія з чітким підтвердженням.

Не можна вивантажувати середовище без попередження, якщо воно:

- зараз виконується;
- очікує на відповідь користувача;
- має незбережені зміни.

### Збереження списку між запусками

FlowAI зберігає реєстр середовищ у локальних налаштуваннях програми:

- унікальний ID середовища;
- шлях до `.flowai.json`;
- відображувану назву;
- порядок у списку.

Токени ChatGPT, промпти й результати агентів не слід зберігати в цьому реєстрі.
Після перезапуску список відновлюється, але всі елементи спочатку мають сірий стан,
доки користувач не завантажить їх.

Якщо файл переміщено або видалено, елемент залишається у списку, а при його
відкритті FlowAI показує повідомлення **Файл не знайдено**. Середовище можна
прибрати зі списку через контекстне меню.

### Блоки, що потребують втручання

Стан `needs_attention` виникає, коли блок **Result** вичерпав ліміт проходів
однією зі своїх гілок або коли для нього увімкнено ручне підтвердження перед
переходом. Правила описані в розділі
[Цикл переробки і ліміти Result](#цикл-переробки-і-ліміти-result).

При досягненні ліміту FlowAI:

1. зберігає контрольну точку виконання в поточному сеансі програми;
2. призупиняє лише поточне середовище;
3. встановлює `needs_attention`;
4. показує трикутник у боковій панелі, а сам блок починає блимати;
5. відкриває вікно з описом ситуації після кліку по блоку;
6. після відповіді продовжує з наступного кроку, не запускаючи завершені блоки
   повторно.

Якщо в цей момент головне вікно неактивне, FlowAI показує системне сповіщення
Windows. Натискання на нього відновлює вікно, вибирає потрібне середовище та
фокусує блок, який очікує на користувача. Так само працює сповіщення про повне
завершення фонового Flow.

### Модель даних

Кожне середовище представлене окремою сесією:

```text
WorkspaceSession
├── id, project_path, display_name
├── workflow, load_state, dirty
├── run_state: idle | running | needs_attention | failed | completed | cancelled
├── unread_result
├── log_text, run_events, node_statuses
├── node_durations, node_duration_history, node_started_at
├── node_stages, port_counts, log_entries
├── checkpoint, run_directory
├── intervention_responses, pending_intervention
├── canvas_transform, scroll, selected_object
├── undo_history, redo_history
└── run_thread, run_worker, stop_requested
```

`MainWindow` керує колекцією `WorkspaceSession`. Кожна сесія має власний Workflow,
фоновий Runner, журнал, контрольну точку, стани нод і дані незавершеного втручання.

Глобальними залишаються:

- профіль ChatGPT;
- інформація про ліміти;
- розташування dock-панелей та остання папка файлових діалогів;
- реєстр збережених робочих середовищ.

Глобальної черги або обмеження кількості одночасних запусків у версії 0.3.0 немає:
кожне середовище може мати власний фоновий `QThread` із Runner.

## Подальші рекомендовані покращення

Нижче наведені наступні доповнення після реалізації базової багатопроєктної
системи.

### 1. Контрольні точки та продовження Flow

FlowAI вже зберігає результат завершених нод у пам’яті та не повторює їх після
втручання користувача. Наступне покращення — записувати контрольну точку на диск,
щоб продовжувати Flow після перезапуску програми або системного збою.

### 2. Повторний запуск з вибраної ноди

Додати дії:

- **Запустити тільки цю ноду**;
- **Запустити від цієї ноди**;
- **Повторити невдалу ноду**;
- **Використати збережені результати попередніх нод**.

Перед повторним запуском FlowAI має показувати, які наступні результати будуть
визнані застарілими.

### 3. Інспектор даних

Для кожної ноди показувати окремі вкладки:

- **Вхідні дані**;
- **Сформований промпт**;
- **Відповідь**;
- **Структурований JSON**;
- **Помилка**;
- **Час і використана модель**.

Це значно спростить пошук неправильних `source_path`, змінних і шаблонів.

### 4. Історія запусків у кожному середовищі

Показувати список запусків із датою, статусом, тривалістю та можливістю відкрити
результати. Непрочитаний результат має бути прив’язаний до конкретного запуску, а
не лише до всього проєкту.

### 5. Черга і ліміт паралельних запусків

Дозволити кільком середовищам працювати у фоні, але встановити глобальне обмеження,
наприклад 1–3 одночасні агентські блоки. Решта запусків отримують стан **У черзі**. Це
захищає ліміти Codex і робить навантаження передбачуваним.

У профілі варто додатково показувати:

```text
Працює: 2 · У черзі: 3 · Потребує уваги: 1
```

### 6. Сповіщення — реалізовано

Коли фоновий Flow завершився або потребує втручання, FlowAI показує системне
сповіщення Windows. Натискання на нього відкриває потрібне середовище й фокусує
відповідний блок.

Звуки повинні бути вимкненими за замовчуванням і налаштовуватися окремо.

### 7. Чернетки замість агресивного автозбереження

Незбережені зміни кожного середовища варто автоматично записувати у локальну
чернетку, не перезаписуючи основний `.flowai.json`. Після аварійного завершення
FlowAI пропонує відновити чернетку.

### 8. Версії промптів і порівняння результатів

Зберігати історію постійних інструкцій, промптів і вибраних моделей. Додати
порівняння двох запусків, щоб бачити, як зміна моделі або промпту вплинула на
відповідь.

### 9. Сховище секретів

Додати локальне захищене сховище для токенів сторонніх сервісів. У Flow повинні
зберігатися лише посилання виду `{{secret.GITHUB_TOKEN}}`, а не самі значення.
Секрети не можна показувати в журналі чи передавати нодам без явного дозволу.

### 10. Доступність і навігація

- `Ctrl+1`…`Ctrl+9` — швидке перемикання між першими середовищами;
- `Ctrl+Tab` — наступне середовище;
- перетягування для зміни порядку;
- закріплення важливих Flow угорі;
- текстові статуси та форми іконок на додачу до кольорів;
- режим підвищеного контрасту.

### Пріоритет наступних етапів

| Етап | Статус | Що реалізувати |
| --- | --- | --- |
| P0 | Готово | Сесії, бокова панель, окремі фонові Runner і журнали |
| P0 | Готово | Незалежні стани завантаження, вибору, виконання та непрочитаного результату |
| P1 | Готово | Ноди втручання і продовження з контрольної точки в поточному сеансі |
| P1 | Наступний | Збереження контрольної точки на диск і відновлення після перезапуску |
| P1 | Готово | Системні сповіщення Windows із переходом до середовища та ноди |
| P1 | Наступний | Черга та глобальне обмеження паралельності |
| P2 | Заплановано | Інспектор даних та історія запусків |
| P2 | Заплановано | Чернетки, зміна порядку, закріплення і гарячі клавіші |
| P3 | Заплановано | Версії промптів і сховище секретів |

## Створення першого Flow

Виберіть **Файл → Новий** або натисніть `Ctrl+N`, щоб створити проєкт із готовою
схемою:

```text
Entry prompt → Prompt Reviewer → Task Executor → Task Reviewer → Result
                                        ▲                          │
                                        └────────── FALSE ─────────┘
```

Збоку стоїть блок **Work Reviewer**, який веде протокол роботи всього Flow.

1. Виберіть блок **Entry prompt** і опишіть завдання, за потреби прикріпіть файли
   та картинки.
2. У **Prompt Reviewer** за потреби змініть модель і постійні інструкції.
3. У **Task Executor** виберіть модель, рівень міркування та доступ до файлів.
4. У **Task Reviewer** перевірте, який блок вибрано еталоном.
5. У **Result** задайте ліміти проходів TRUE і FALSE, за потреби файл для
   збереження результату та прапорець **Очікувати підтвердження перед переходом**.
6. Натисніть **Run**.

Готовий приклад міститься у файлі:

```text
examples\review_loop.flowai.json
```

## Типи блоків

Кожен блок має короткий ідентифікатор, показаний у шапці та в Інспекторі.
Чотири блоки з шести запускають окремий потік Codex: **Prompt Reviewer**,
**Task Executor**, **Task Reviewer** і **Work Reviewer**.

### Entry prompt

Вхідна точка Flow: сюди користувач вставляє промпт і прикріплює файли.

Налаштування:

- **Вхідний промпт** — основне завдання;
- **Початковий JSON** — додаткові структуровані дані;
- **Файли і картинки** — локальні вкладення.

Результат:

```json
{
  "status": "success",
  "text": "Вхідний промпт",
  "data": {
    "text": "Вхідний промпт",
    "task": "Вхідний промпт",
    "attachments": ["C:/макет.png"]
  }
}
```

Вкладення передаються далі через `data.attachments`. Картинки
(`.png`, `.jpg`, `.jpeg`, `.webp`, `.gif`, `.bmp`) передаються моделі як
зображення, решта файлів — як локальні шляхи в тексті промпту.

В Інспекторі картинки показуються мініатюрами й відкриваються на весь екран
лівим кліком. Інші вкладення відображаються лише назвою файла. Через контекстне
меню можна перейти до файла у Провіднику, скопіювати його шлях або прибрати зі
списку без видалення з диска.

### Prompt Reviewer

Покращує вхідний промпт, розуміючи, через які блоки задача пройде далі.

Крім звичайних налаштувань агента отримує спеціальний плейсхолдер:

- `{{flow_chain}}` — впорядкований опис наступних блоків: короткий id, тип, назва,
  промпт і ліміти Result;
- `{{entry_prompt}}` — початковий промпт користувача.

Повертає JSON:

```json
{
  "improved_prompt": "Уточнена задача",
  "notes": ["що саме змінено"]
}
```

Поле `improved_prompt` стає текстовим результатом блоку, тому з’єднання
`text → prompt` передає покращений промпт наступному блоку без додаткових
налаштувань.

### Task Executor

Виконує задачу. Це звичайний Codex-агент, у якого **Джерело промпту** за
замовчуванням — вхідна змінна `prompt`.

Головна особливість — поле **Пам’ять між спробами**:

- `Той самий тред` (за замовчуванням) — при поверненні задачі на переробку блок
  продовжує той самий потік Codex через `thread_resume`. Агент пам’ятає, що вже
  зробив, і отримує лише зауваження рев’ювера;
- `Новий тред щоразу` — кожна ітерація починається з чистого контексту.

### Task Reviewer

Перевіряє, чи результат виконавця задовольняє поставленій задачі.

Налаштування, крім звичайних агентських:

- **Блок-еталон** — блок, чий результат вважається постановкою задачі. За
  замовчуванням `Авто`: найближчий вгору по графу **Prompt Reviewer**, а якщо його
  немає — **Entry prompt**. Значення підставляється у промпт як `{{criteria}}`.

Формат відповіді фіксований:

```json
{
  "verdict": true,
  "score": 90,
  "candidate_path": "C:/проєкт/final.png",
  "reason": "Чому прийнято або відхилено",
  "must_fix": [
    {
      "id": "zone_01",
      "bbox": [10, 20, 110, 220],
      "restore_from": "C:/проєкт/source.png",
      "allowed_change": "Що дозволено змінити",
      "acceptance": "Машинно перевірювана умова приймання"
    }
  ]
}
```

`must_fix` може лишатися масивом коротких рядків у простих Flow. Для циклів із
файлами рекомендована структурована форма вище: Result передає її назад без
сплющення разом із фактичним `candidate_path` і повним останнім висновком.

Якщо агент повернув не JSON або без поля `verdict`, блок завершується помилкою.
Налаштовані **Повторні спроби** застосовуються і тут.

### Result

Розгалужує Flow за вердиктом і водночас формує фінальний результат.

Налаштування:

- **Шаблон результату** — текст, який формується на гілці TRUE;
- **Зберегти у файл** — необов’язковий шлях; запис відбувається лише на TRUE;
- **Ліміт проходів TRUE** — за замовчуванням 1;
- **Ліміт проходів FALSE** — за замовчуванням 3;
- **Очікувати підтвердження перед переходом** — за замовчуванням вимкнено. Якщо
  ввімкнути, Result після визначення гілки зупиняється до кліку по блоку й кнопки
  **Продовжити**, щоб користувач міг перевірити проміжні створені файли.

Вердикт береться зі вхідних даних: спочатку зі змінної `verdict`, потім із
`review.verdict`, `task_review.verdict` або `verdict_data.verdict`, а потім із
будь-якої вхідної структури, що містить поле `verdict`.
Рекомендоване з’єднання від Task Reviewer — `data → review`: так у Result
потрапляють і вердикт, і причина.

Результат блоку:

```json
{
  "verdict": true,
  "branch": "true",
  "result": "Фінальний текст",
  "saved_to": "C:/проєкт/final.md",
  "reason": "Висновок рев’ювера",
  "must_fix": [],
  "candidate_path": "C:/проєкт/final.png",
  "review": {"verdict": true},
  "retry_context": {
    "reason": "Висновок рев’ювера",
    "must_fix": [],
    "candidate_path": "C:/проєкт/final.png",
    "previous_review": {"verdict": true}
  },
  "forced": false
}
```

Для петлі переробки рекомендовано з’єднати
`Result: data.retry_context → Task Executor: prompt`. Тоді виконавець отримує
лише найновіший структурований висновок, а після кожного його проходу маршрут
знову обов’язково веде через Task Reviewer.

Абсолютний шлях збереження використовується без змін, відносний обчислюється від
робочої папки Flow, відсутні вкладені папки створюються автоматично.

### Work Reviewer

Блок-спостерігач без портів. Не бере участі в маршруті — його не можна з’єднати
з іншими блоками, і в одному Flow він може бути лише один.

Налаштування:

- **Спостерігати всі блоки Flow** — увімкнено за замовчуванням; до протоколу
  потрапляють усі блоки, крім самого Work Reviewer, а нові блоки додаються
  автоматично;
- **Блоки під наглядом** — список із галочками, якщо потрібен не весь Flow;
- **Файл звіту** — куди зберегти аналіз; за замовчуванням
  `runs/<запуск>/work-review-report.md`.

Докладно — у розділі
[Протокол роботи і Work Reviewer](#протокол-роботи-і-work-reviewer).

### Спільні налаштування агентських блоків

- **Модель** — наприклад `gpt-5.6-sol`, `gpt-5.6-terra` або `gpt-5.6-luna`;
- **Міркування** — `none`, `low`, `medium`, `high`, `xhigh` або `max`;
- **Доступ** — `read-only`, `workspace-write` або `full-access`;
- **Пам’ять між спробами** — той самий тред або новий щоразу;
- **Додаткові папки блоку** — папки, доступні лише цьому агенту;
- **Постійні інструкції** — передаються при кожному запуску блоку;
- **MD-інструкції** — файли `.md`/`.markdown`, вміст яких FlowAI читає і додає до
  постійних інструкцій;
- **Джерело промпту** — власне поле **Промпт** або вхідна змінна `prompt`;
- **Формат відповіді** і **Схема JSON**;
- **Файли і картинки** — вкладення саме цього блоку;
- **Повторні спроби** — від 0 до 5 повторів після помилки.

Поле моделі редаговане: можна ввести інший ідентифікатор, якщо він підтримується
поточним Codex і доступний у вашому тарифі.

На картці агентського блока модель показується разом із вибраним типом
**Міркування**. Під час виконання всі незмінні параметри ноди блокуються. Числові
поля й списки не реагують на колесо миші, доки користувач прокручує Parameters.

Перед викликом Codex FlowAI формує промпт із секцій: завдання, необов’язкова
вказівка користувача після вичерпання ліміту, інші вхідні дані, доступні робочі
папки, локальні вкладення та вимога до JSON. Текстові постійні інструкції й вміст
MD-файлів передаються окремо як developer instructions. Підтримувані зображення
додатково передаються SDK як мультимодальний локальний вхід; інші вкладення
залишаються шляхами у промпті.

Файловий Executor може мати службові поля JSON-конфігурації
`required_output_path`, `protected_source_path` і, за потреби,
`protected_source_sha256`. У такому разі FlowAI після кожного проходу перевіряє,
що виконавець створив або атомарно оновив саме обов’язковий файл, повернув цей
шлях у `candidate_path`/`output_path`, а захищений оригінал не змінився. У вихідні
дані автоматично додається `artifact` із шляхом, розміром, часом зміни та SHA-256.
Старий файл, який не було оновлено в поточному проході, не передається далі як
новий результат.

FlowAI намагається розпізнати JSON у кожній відповіді. Для звичайного тексту в
`data` записується `{ "response": "..." }`. **Task Reviewer** є суворішим: його
відповідь обов’язково має бути JSON-об’єктом із полем `verdict`. У **Prompt
Reviewer** значення `improved_prompt`, якщо воно є, стає вихідним `text`.

Під час одного запуску FlowAI відкриває один локальний клієнт Codex, але кожен
агентський блок має власний Codex-тред. Ідентифікатори тредів зберігаються в
контрольній точці окремо за ID блока:

- режим **Той самий тред** відновлює тред при наступній ітерації цього блока;
- режим **Новий тред щоразу** не використовує збережений ID;
- якщо відновити старий тред не вдалося, адаптер автоматично створює новий.

**Повторна спроба** означає повтор після технічної помилки в межах одного проходу
блока. **Наступна ітерація** означає новий прохід схеми, наприклад після повернення
Result гілкою FALSE. Це різні механізми.

## Цикл переробки і ліміти Result

З’єднання, що виходить із порту FALSE блоку Result назад у Task Executor, утворює
цикл. Це єдиний дозволений вид циклу: FlowAI перевіряє, що будь-який цикл у схемі
проходить через блок Result. Цикл в обхід Result — помилка валідації.

### Як рахуються проходи

Кожна гілка має власний лічильник проходів за один запуск. Перед тим як пропустити
потік у гілку, FlowAI перевіряє її ліміт:

- поки пройдено менше за ліміт — потік іде далі, лічильник зростає;
- на спробі перевищити ліміт Flow зупиняється і чекає на користувача.

Актуальні значення показані просто на полотні біля портів, наприклад `FALSE 2/3`.

Ліміти TRUE/FALSE можна змінити у Parameters навіть тоді, коли Flow уже працює.
Зміна передається активному Runner одразу й застосовується під час наступної
перевірки Result, тому для цього не потрібно перезапускати проєкт.

Додатково діє загальний запобіжник: якщо Flow виконав понад 200 кроків, запуск
зупиняється з помилкою про ймовірне зациклення.

### Вікно вичерпаного ліміту

Блок починає блимати, а в боковій панелі з’являється трикутник. Клік по блоку
відкриває вікно, у якому показано:

- яка гілка вибрана і скільки разів вона вже пройдена з дозволеного;
- останній висновок Task Reviewer із переліком `must_fix`.

Доступні дії:

- **Додати N спроб** — збільшити ліміт цієї гілки і продовжити. У полі
  **Вказівка агенту** можна дописати вимогу від себе: вона потрапить у промпт
  наступної спроби окремою секцією;
- **Піти іншою гілкою** — примусово продовжити протилежною гілкою, ігноруючи
  вердикт. Лічильник іншої гілки при цьому не витрачається;
- **Зупинити Flow** — завершити запуск.

Після відповіді Flow продовжується з контрольної точки: уже виконані блоки
повторно не запускаються, а Task Executor продовжує свій Codex-тред.

Якщо увімкнено **Очікувати підтвердження перед переходом**, Result переходить у
той самий стан `needs_attention` перед кожним переходом, навіть коли ліміт ще не
вичерпано. Клік по блоку показує знайдені проміжні файли та кнопки **Продовжити**
і **Зупинити**. Продовження не витрачає додатковий прохід і не запускає завершені
ноди повторно.

## Протокол роботи і Work Reviewer

Якщо у Flow є блок **Work Reviewer**, FlowAI веде протокол роботи всіх блоків.
Протокол наповнює сам рушій — агентів ні про що не просять, тому дані повні й не
залежать від того, чи агент виконав додаткову інструкцію та чи має він право
запису.

### Файл протоколу

Перед першим блоком створюється файл:

```text
runs\YYYYMMDD-HHMMSS-microseconds\work-review.md
```

У шапці — назва Flow, час запуску, статус і пояснення структури. Далі йде секція
на кожен спостережуваний блок, названа його коротким id:

```text
## 7f3a9c · Task Executor «Task Executor»
```

Після кожного проходу блоку в його секцію дописується запис:

- номер проходу, статус і тривалість;
- модель, рівень міркування та режим доступу;
- Codex-тред і чи був він продовжений;
- шляхи вкладень;
- повний промпт і постійні інструкції;
- реальні кроки агента, отримані від Codex SDK: план, міркування, виклики
  інструментів, виконані команди;
- отриманий результат або текст помилки;
- для Result — гілка, вердикт і причина.

Щоб протокол не зростав безмежно, одне текстове поле у записі обрізається після
6000 символів, а короткий опис одного нормалізованого кроку Codex — після 4000
символів.

Протокол переживає паузу на ліміті: після продовження запису дописуються далі, а
не починаються з нуля.

### Аналіз

Коли Flow завершився — успішно, з помилкою чи зупинкою, — рушій запускає блок
Work Reviewer як звичайного агента, передавши йому протокол вкладенням і шлях
через `{{protocol_path}}`. Результат зберігається у файл звіту, а в журналі
з’являється повідомлення зі шляхом до нього.

Якщо аналіз не вдався, запуск не вважається невдалим: у журнал потрапляє
повідомлення про помилку аналізу.

## З’єднання і передавання даних

### Створення з’єднання

1. Затисніть ліву кнопку миші на вихідному круглому порті справа від початкового
   блоку. У блока Result портів два — вибирайте зелений `TRUE` або червоний
   `FALSE`.
2. Не відпускаючи кнопку, протягніть видиму пунктирну криву до вхідного порту
   зліва від наступного блоку. Допустимий порт під курсором стане яскравішим і
   отримає світний ореол; якщо відвести курсор, він одразу згасне. Порт не
   підсвічується, якщо таке з’єднання вже існує або веде в той самий блок.
3. Відпустіть кнопку на вхідному порті. Якщо відпустити її в порожньому місці,
   попередня лінія зникне й Flow не зміниться.
4. Виділіть створену лінію та налаштуйте її в Інспекторі.

Альтернативний спосіб залишився доступним: один клік по вихідному порту, потім
один клік по вхідному.

Колір лінії повторює колір порту, з якого вона вийшла, тому гілку переробки видно
на схемі одразу. Під час перетягування крива також використовує колір вибраного
виходу.

FlowAI не дозволяє з’єднати блок сам із собою, створити друге однакове з’єднання
з того самого порту або підключити блок **Work Reviewer**, у якого портів немає.

### Зміна форми зв’язку

Подвійний клік у будь-якому місці лінії створює на ній фіолетову керовану точку.
Точку можна вільно перетягувати, а зв’язок плавно проходить через неї та змінює
форму. На одному зв’язку дозволено створити кілька точок; FlowAI вставляє їх у
порядку від вихідної до вхідної ноди.

Координати зберігаються у полі `control_points` відповідного зв’язку в JSON Flow,
тому форма відновлюється після перемикання середовища, Undo/Redo і перезапуску
програми. Щоб прибрати точку, виділіть її та натисніть `Delete` або `Backspace`.

### Поля з’єднання

| Поле | Призначення |
| --- | --- |
| **Підпис** | Текст, показаний над лінією |
| **Що передати** | Шлях у результаті початкової ноди |
| **Вхідна змінна** | Ім’я значення в наступній ноді |
| **Умова переходу** | Вираз, який активує або вимикає маршрут |
| **Перетворення** | Необов’язковий шаблон над вибраним значенням |

Кожна успішна нода створює результат такої форми:

```json
{
  "node_id": "...",
  "status": "success",
  "text": "Людинозрозумілий текст",
  "data": {},
  "error": "",
  "started_at": "...",
  "finished_at": "...",
  "duration_seconds": 1.234
}
```

Приклади поля **Що передати**:

- `$` — увесь результат ноди;
- `data` — структуровані дані;
- `data.summary` — вкладене поле `summary`;
- `data.items.0` — перший елемент масиву;
- `text` — текстовий результат;
- `status` — статус виконання.

Приклад налаштування:

```text
Що передати: data.summary
Вхідна змінна: research
```

У наступній ноді значення буде доступне як `{{research}}`.

### Готові пресети з’єднань

В Інспекторі з’єднання є дві кнопки, які заповнюють поля за вас:

- **Передати відповідь як промпт наступному блоку** — встановлює
  `Що передати: text` і `Вхідна змінна: prompt`. У блоці-приймачі виберіть
  **Джерело промпту → Вхід «prompt» від попереднього блоку** (для Task Executor це
  вже так за замовчуванням);
- **Передати вердикт у Result** — встановлює `Що передати: data` і
  `Вхідна змінна: review`, щоб у Result потрапили і вердикт, і причина.

Інші вхідні змінні продовжують передаватися блоку як додаткові вхідні дані. Якщо
змінна `prompt` відсутня або порожня, FlowAI зупинить блок із чітким
повідомленням про помилку.

Якщо кілька активних з’єднань записують значення в однакову вхідну змінну, перше
значення зберігається як є, а наступні об’єднуються з ним у список.

### Умова переходу

У виразі з’єднання доступні:

- `source` — повний результат початкової ноди;
- `value` — значення, вибране полем **Що передати**;
- `outputs` — результати всіх уже виконаних нод за їхніми ID.

Приклади:

```text
source.status == "success"
source.data.matched == true
value.score >= 80
```

Порожня умова означає безумовний перехід після успішного виконання початкової
ноди.

### Перетворення на з’єднанні

Якщо поле **Перетворення** заповнене, наступна нода отримує результат шаблону, а
не початкове значення. Доступні `{{value}}`, `{{source}}`, `{{outputs}}` і вже
зібрані `{{inputs}}`.

```text
Короткий зміст для наступного агента:
{{value}}
```

## Шаблони

FlowAI використовує прості підстановки `{{шлях}}`.

Приклади:

```text
{{inputs}}
{{task}}
{{research.summary}}
{{items.0.title}}
{{workflow.name}}
```

У нодах доступні:

- `inputs` — об’єкт з усіма вхідними змінними;
- кожна вхідна змінна окремо;
- `workflow.name` — назва поточного Flow.

Складні об’єкти та списки автоматично перетворюються на форматований JSON. Якщо
шлях не знайдено, плейсхолдер залишається в тексті — це допомагає помітити помилку
в назві змінної.

Шаблони не виконують функції, арифметику чи Python-код.

## Умовні вирази

Вирази підтримують:

- значення `true`, `false`, `null`;
- рядки, числа, списки, кортежі та словники;
- доступ через крапку: `inputs.status`;
- доступ за індексом: `inputs.items[0]`;
- `not`, `and`, `or`;
- `==`, `!=`, `>`, `>=`, `<`, `<=`;
- `in`, `not in`, `is`, `is not`.

Приклади:

```text
inputs.status == "ready"
inputs.score >= 80 and inputs.category in ["A", "B"]
not inputs.blocked
source.data.matched is true
```

Виклики функцій, імпорти, арифметичні операції та доступ до атрибутів Python-об’єктів
заборонені.

## Порядок виконання

1. FlowAI перевіряє наявність блоків, коректність з’єднань і те, що всі цикли
   проходять через Result.
2. Створює знімок поточних налаштувань Flow.
3. Ставить у чергу блоки без вхідних з’єднань.
4. Бере з черги блок, у якого всі попередники вже відпрацювали, виконує його і
   передає результат по активних вихідних з’єднаннях.
5. Повторює, доки черга не спорожніє.
6. Після завершення зберігає машинозчитуваний журнал і, за наявності Work
   Reviewer, звіт про роботу блоків.
7. Оновлює відсоток лімітів профілю.

На відміну від версії 0.2, блок може виконуватися кілька разів за один запуск —
саме так працює цикл переробки. Порядок вибору з черги враховує топологію схеми,
тому блок із кількома входами (наприклад, Result, який чекає і роботу виконавця,
і вердикт рев’ювера) не запуститься раніше за своїх попередників.

Блок без активного маршруту не додається до черги й не запускається. Окремий
статус `skipped` рушій версії 0.3.0 не створює.

Для блоків **Entry prompt** і **Result** операція виконується безпосередньо
Python-кодом FlowAI. Для агентських блоків запускається окремий потік Codex.

Незалежні гілки в поточній версії виконуються послідовно, а не паралельно.

Помилка блоку зупиняє весь Flow. Налаштовані повторні спроби виконуються до того,
як помилка стане фінальною.

Кнопка **Stop** встановлює запит на скасування, одразу викликає переривання
активного `TurnHandle` Codex і не запускає наступні блоки чи Work Reviewer.
Зупинка діє на всі генерації вибраного проєкту, але не зачіпає Flow, запущені в
інших робочих середовищах.

### Сон, блокування Windows і закриття програми

FlowAI відстежує перехід системи у сон та блокування сеансу Windows. Активні
Runner переходять у керовану паузу; якщо модель саме виконувала запит, цей turn
переривається без витрачання налаштованої повторної спроби. Після пробудження або
розблокування блок запускає цей самий прохід знову й продовжує маршрут.

Якщо хоча б одне середовище виконується, зупиняється або очікує втручання,
закриття FlowAI показує попередження й не закриває програму. Спочатку потрібно
зупинити активні Flow або завершити очікувану взаємодію.

## Файли Flow і журнали

### Файл проєкту

FlowAI зберігає схеми у форматі:

```text
назва.flowai.json
```

Якщо розширення не вказане, програма додає `.flowai.json` автоматично. Запис
виконується через тимчасовий файл, після чого він замінює основний.

Основні секції:

```json
{
  "format_version": 2,
  "name": "Назва Flow",
  "workspace": "",
  "additional_folders": [],
  "nodes": [],
  "edges": []
}
```

Дані входу ChatGPT і токени авторизації у файл Flow не записуються.

### Робоча папка

Основна робоча папка визначається так:

1. **Основна робоча папка** з **Налаштувань Flow**;
2. папка, де збережено `.flowai.json`;
3. поточна папка запуску програми для ще не збереженого Flow.

Ця папка стає основною для кожного блока. У налаштуваннях Flow можна додати спільні
додаткові папки для всіх агентів, а в Інспекторі агентського блока — папки лише
для вибраного агента. Кожен список має кнопки **Додати папку** та **Прибрати**. Основну папку
можна очистити кнопкою **Прибрати**, після чого знову діятиме автоматичний вибір.

Усі вказані папки повинні існувати до запуску. Для `workspace-write` додаткові
папки передаються Codex як `sandbox_workspace_write.writable_roots`, тому агент
може записувати в них, не отримуючи повного доступу до файлової системи.

### Журнали запусків

Кожен запуск отримує власну папку:

```text
runs\YYYYMMDD-HHMMSS-microseconds\
├── flowai-run.json          машинозчитуваний журнал подій
├── work-review.md           протокол роботи блоків (якщо є Work Reviewer)
└── work-review-report.md    аналіз роботи блоків
```

Для збереженого Flow папка `runs` створюється поруч із файлом проєкту. Для
незбереженого — у поточній папці програми.

Журнал `flowai-run.json` містить:

- назву Workflow;
- ID робочого середовища;
- статус `success`, `failed`, `cancelled` або проміжний `needs_attention`;
- загальну помилку;
- повний список подій і результатів блоків.

Кожен результат блока має `duration_seconds`. На картці ноди проходи також
показуються окремими таймерами: повторний запуск починає новий відлік від нуля,
не додаючи його до попереднього.

Під час очікування користувача цей самий файл записується зі статусом
`needs_attention`. Після продовження або зупинки він перезаписується фінальним
станом того самого запуску.

Увага: промпти, відповіді та передані дані потрапляють і в журнал, і в протокол
роботи. Не додавайте секретні дані, якщо ці файли зберігатимуться у спільній
папці.

### Діагностичні журнали програми

Окрім журналів окремих Flow, FlowAI постійно веде два загальні файли:

```text
%LOCALAPPDATA%\FlowAI\logs\
├── flowai.log    запуск і завершення програми, події Flow та звичайні помилки
└── crash.log     необроблені винятки, аварійні збої та зависання інтерфейсу
```

Відкрити цю папку можна через **Допомога → Відкрити папку логів**. Обидва файли
мають обмежений розмір і автоматичну ротацію; попередні версії отримують суфікси
`.1`, `.2` тощо.

Глобальні винятки Python, помилки фонових потоків і критичні повідомлення Qt
записуються у `crash.log` із traceback. Якщо головний потік інтерфейсу не подає
ознаки роботи протягом 15 секунд, watchdog записує у цей файл стеки всіх Python-
потоків. Це дає діагностичні дані навіть для зависання без звичайного винятку.

Щоб не перевантажувати інтерфейс великими даними, повний промпт агента лишається
у `flowai-run.json` і протоколі запуску, а в екранному журналі показується коротке
повідомлення. Екранний журнал також має ліміт розміру; це не обрізає збережений
машинозчитуваний журнал запуску.

Екранний журнал зберігається окремо для кожного робочого середовища. Повідомлення
під час роботи мають формат `короткий id ноди: повідомлення` і забарвлюються
кольором ноди. Шляхи файлів, які були створені або виявлені у результаті агента,
підкреслюються.

## Безпека

### Рівні доступу агента

| Режим | Можливості |
| --- | --- |
| `read-only` | Читання дозволених даних без запису у workspace |
| `workspace-write` | Читання і запис у робочій папці |
| `full-access` | Повний доступ до файлової системи в межах можливостей Codex |

Перед запуском нод із `full-access` FlowAI показує окреме попередження зі списком
таких агентів. Використовуйте цей режим лише для перевірених Flow.

Додаткові рекомендації:

- перевіряйте постійні інструкції та промпти перед запуском;
- відкривайте чужі `.flowai.json` як потенційно небезпечні автоматизації;
- не зберігайте паролі або токени у промптах, вкладеннях і початковому JSON;
- не публікуйте файл `%USERPROFILE%\.codex\auth.json`;
- для аналізу документів без змін використовуйте `read-only`;
- для генерації файлів у проєкті використовуйте `workspace-write`.

## Типові помилки

### Команда `python` не знайдена

Установіть Python 3.10+ і ввімкніть опцію додавання Python до `PATH`, після чого
повторно запустіть `install.ps1`.

### Кнопка показує «Увійти в ChatGPT»

Сеанс Codex відсутній або завершився. Натисніть кнопку та пройдіть авторизацію у
браузері. Також можна виконати:

```powershell
codex login
```

### Відсоток ліміту не показується

FlowAI продовжує показувати профіль, навіть якщо сервіс лімітів тимчасово
недоступний. Перевірте інтернет і зачекайте до наступного автоматичного оновлення
або перезапустіть програму.

### Модель недоступна

Перевірте правильність ідентифікатора моделі та її доступність у вашому тарифі.
Поле моделі дозволяє довільний текст, але Codex відхилить непідтримувану модель під
час запуску.

### «Робоча папка не існує»

Відкрийте **Settings** або список додаткових папок агентського блока. Виберіть
наявну папку чи приберіть зі списку шлях, який більше не існує.

### Блок не запускається

У версії 0.3.0 блок, до якого не дійшов жоден активний маршрут, просто не
потрапляє до черги. Перевірте:

- статус попередньої ноди;
- поле **Умова переходу**;
- шлях **Що передати**;
- назву вхідної змінної.

### Flow містить цикл, який не проходить через Result

Зворотні зв’язки дозволені лише з виходів `TRUE` і `FALSE` блоку Result — саме
його лічильники не дають Flow крутитися вічно. Видаліть з’єднання, яке повертає
дані до вже пройденого блоку в обхід Result.

### Перевищено ліміт кроків

Спрацював загальний запобіжник на 200 кроків. Перевірте ліміти проходів блоку
Result: надто великі значення дозволяють Flow крутитися дуже довго.

### Блок Result не отримав вердикт

Проведіть у Result з’єднання від Task Reviewer і скористайтеся пресетом
**Передати вердикт у Result** (`data → review`).

### Формат Flow 1 більше не підтримується

Набір блоків повністю змінився у версії 0.3. Створіть Flow заново — автоматичної
конвертації немає.

### JSON позначено червоним

Виправте синтаксис: подвійні лапки, коми, дужки та назви полів. Підказка поля
містить повідомлення JSON-парсера.

### Зупинка не відбулася миттєво

Це очікувана поведінка. FlowAI чекає завершення активного запиту Codex і не запускає
наступну ноду.

## Розробка і тестування

Установлення в режимі редагування виконує `install.ps1`. Запуск тестів:

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

`ruff` не входить до стандартних залежностей FlowAI. Для необов’язкового статичного
аналізу спочатку встановіть його, а потім запустіть перевірку:

```powershell
.\.venv\Scripts\python.exe -m pip install ruff
.\.venv\Scripts\ruff.exe check .
```

Перевірка інтерфейсу без відкриття вікна:

```powershell
$env:QT_QPA_PLATFORM = "offscreen"
.\.venv\Scripts\python.exe -m flowai
```

Тестовий режим без реального звернення до Codex:

```powershell
$env:FLOWAI_FAKE_CODEX = "1"
.\.venv\Scripts\python.exe -m flowai
```

У цьому режимі агентський блок повертає текст із назвою моделі та сформованим
промптом. Виклики також накопичуються у тестовому списку `FAKE_CALLS`, що дає
змогу перевіряти відновлення тредів і передані вкладення.

## Поточні обмеження

- GPT-моделі працюють у хмарі; повністю офлайн-режиму немає.
- Цикл дозволений лише через блок Result; довільні цикли не підтримуються.
- Незалежні гілки виконуються послідовно.
- Контрольна точка зберігається в пам’яті й поки не відновлюється після закриття
  програми.
- Візуальні окремі таймери проходів належать поточній сесії та не відновлюються
  після перезапуску програми; час кожного проходу залишається у
  `flowai-run.json` і Markdown-протоколі.
- Немає глобальної черги або обмеження кількості одночасних фонових Flow.
- Файли формату 1 не конвертуються — такі Flow потрібно створити заново.
- Відсутній окремий менеджер секретів.
- Параметр `timeout_seconds` може бути присутній у JSON конфігурації агента, але в
  поточній версії не обмежує тривалість SDK-запиту.
- Не зображувальні вкладення передаються агенту як локальні шляхи у промпті;
  окремим мультимодальним входом SDK надсилаються лише підтримувані локальні
  зображення.
